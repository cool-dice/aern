# Артефакт 22. AI pipeline

## 1. Общие принципы

- AI-бот — полноценный персонаж мира. Он берёт квесты, торгует, крафтит, воюет, исследует, общается, вступает в гильдии, создаёт гильдии, предаёт, ошибается и умирает по общим правилам.
- AI-бот не имеет встроенного знания лора, сюжета, механик или других персонажей. Он узнаёт мир через игру — так же, как игрок.
- Инференс модели выполняется **на клиенте игрока** (GPU носителя). Это разгружает сервер.
- Запуск AI-бота — **обязательное системное требование**. Игрок не может войти в игру, если его оборудование не соответствует минимальным требованиям для инференса.
- Сервер остаётся авторитарным: все действия бота валидируются так же, как действия игрока.
- Один носитель — один активный бот. Бот живёт, пока носитель онлайн. При офлайне носителя бот исчезает из мира, его состояние сохраняется.
- Базовая policy-модель — одна на всех, обновляется централизованно. Персональный адаптер — индивидуальный, дообучается на сервере.
- Модель не является «ИИ-агентом общего назначения». Это узкоспециализированная policy для конкретной игры.

---

## 2. Архитектура pipeline

Поток данных:

```
Сервер (игровое состояние)
        ↓
Perception (клиент) — парсинг состояния в вектор наблюдения
        ↓
Memory (клиент + сервер) — векторная БД, граф знаний
        ↓
Decision (клиент) — policy-модель + LLM
        ↓
Action (клиент) — дискретные команды
        ↓
Сервер (валидация) — принятие или отклонение
        ↓
Обратная связь (награда, лог, память)
```

### 2.1. Компоненты

| Компонент | Где работает | Назначение |
|---|---|---|
| **Perception** | Клиент | Преобразует состояние мира в вектор наблюдения |
| **Memory** | Клиент + сервер | Хранит эпизодическую и семантическую память |
| **Policy** | Клиент | Принимает решения: движение, бой, взаимодействие |
| **LLM** | Клиент | Диалоги, планирование, интерпретация квестов |
| **Action** | Клиент | Формирует команды для сервера |
| **Validator** | Сервер | Проверяет каждое действие по общим правилам |
| **Trainer** | Сервер | Обновляет базовую policy и персональные адаптеры |

## 3. Perception — восприятие

### 3.1. Вход

Сервер передаёт клиенту состояние мира в зоне видимости бота:

| Категория | Данные |
|---|---|
| **Сам бот** | HP, ОД, статы, инвентарь, экипировка, статусы, кулдауны, НН, УПЯ |
| **Локация** | Тип узла, регион, координаты, сейф-зона, владелец |
| **Ближайшие существа** | Игроки, AI, монстры, NPC, Хранители: позиция, HP, тип, враждебность |
| **Объекты** | Сундуки, ресурсные узлы, двери, порталы, трупы, ловушки |
| **События** | Аномалии, вторжения, погода, объявления |
| **Чат** | Локальные сообщения, системные уведомления |
| **Квесты** | Активные, доступные, прогресс |
| **Экономика** | Цены NPC, лоты аукциона, курс бартера |
| **Гильдия** | Состав, ранги, войны, налоги, контракты |
| **Карта** | Исследованные узлы и рёбра |

### 3.2. Преобразование

Perception превращает сырые данные в **вектор наблюдения** фиксированной размерности:

| Блок | Размер | Содержание |
|---|---|---|
| Собственное состояние | 64 | HP, ОД, статы, статусы, кулдауны |
| Пространство | 128 | Сетка 8×8 вокруг бота: тип клетки, существа, объекты |
| Существа | 256 | 16 ближайших существ: тип, HP, дистанция, враждебность |
| Объекты | 128 | 16 ближайших объектов: тип, дистанция, состояние |
| События | 64 | Активные события, их параметры |
| Квесты | 64 | Активные квесты, цели, прогресс |
| Экономика | 32 | Цены, лоты, ресурсы |
| Гильдия | 32 | Ранг, войны, налоги |
| Память | 128 | Вектор из памяти (см. раздел 4) |
| **Итого** | **896** | Вектор наблюдения |

### 3.3. Особенности

- Пространство кодируется **относительно бота**, а не абсолютно.
- Существа кодируются с учётом **враждебности** (отношение, гильдия, титулы).
- Объекты кодируются с учётом **доступности** (ресурсы, ключи, уровень).
- События кодируются с учётом **влияния** на бота (урон, дебафф, лут).

## 4. Memory — память

### 4.1. Типы памяти

| Тип | Где хранится | Назначение |
|---|---|---|
| **Эпизодическая** | Векторная БД (pgvector) | Что произошло: события, встречи, бои, сделки |
| **Семантическая** | Граф знаний | Что известно: факты, связи, правила |
| **Рабочая** | Клиент (RAM) | Текущий контекст: цели, планы, диалоги |
| **Процедурная** | Policy-модель | Навыки: бой, крафт, торговля |

### 4.2. Эпизодическая память

- Запись: `{timestamp, location, event, participants, outcome, reward, tags}`.
- Хранение: pgvector на сервере.
- Поиск: по косинусной близости к текущему контексту.
- Лимит: 10 000 записей на бота.
- Старые записи архивируются, но не удаляются.

### 4.3. Семантическая память

Граф знаний:

| Узел | Рёбра |
|---|---|
| Персонаж | знает, встречал, торговал, воевал, состоит в гильдии |
| Локация | соединена, содержит, опасна, богата |
| Предмет | стоит, крафтится, требуется, найден |
| Квест | выдан, выполнен, провален, награда |
| Гильдия | состав, войны, союзы, налоги |
| Событие | участники, исход, последствия |

- Граф хранится на сервере в PostgreSQL.
- Клиент получает подграф вокруг текущего контекста.

### 4.4. Рабочая память

- Контекст текущего решения: цель, план, диалог, бой.
- Хранится в RAM клиента.
- Ограничена 10 последними событиями.

### 4.5. Процедурная память

- Встроена в policy-модель.
- Не требует отдельного хранения.

## 5. Decision — принятие решений

### 5.1. Двухуровневая архитектура

```
Policy-модель (быстрые решения)
        ↓
LLM (медленные решения, диалоги, планирование)
        ↓
Action
```

- **Policy** принимает решения в реальном времени: движение, атака, использование предмета, отход.
- **LLM** используется для: планирования, диалогов, интерпретации квестов, принятия сложных решений (торговля, гильдии, войны).

### 5.2. Policy-модель

**Архитектура:**

| Слой | Тип | Размер | Активация |
|---|---|---|---|
| Вход | — | 896 | — |
| FC1 | Полносвязный | 1024 | ReLU |
| FC2 | Полносвязный | 1024 | ReLU |
| FC3 | Полносвязный | 512 | ReLU |
| LSTM | Рекуррентный | 512 | tanh |
| Policy head | Полносвязный | 64 | Softmax |
| Value head | Полносвязный | 1 | Linear |

**Выход:** распределение вероятностей по 64 действиям.

**Тип:** PPO (Proximal Policy Optimization) с GAE (Generalized Advantage Estimation).

**Параметры:** ~10 млн параметров. Квантование до 8 бит → ~10 МБ.

### 5.3. LLM

**Архитектура:**

| Параметр | Значение |
|---|---|
| Тип | Трансформер, decoder-only |
| Параметры | 1–3 млрд |
| Контекст | 4096 токенов |
| Квантование | 4 бита |
| Размер | 1–2 ГБ |
| Инференс | llama.cpp / ONNX Runtime |

**Назначение:**

| Задача | Вход | Выход |
|---|---|---|
| Планирование | Цель, контекст, память | Последовательность подцелей |
| Диалог | Реплика собеседника, контекст | Ответ с учётом УПЯ |
| Интерпретация квеста | Описание квеста | Цель, шаги, награда |
| Торговля | Цены, инвентарь, потребности | Решение о сделке |
| Гильдия | Состав, войны, налоги | Голос, предложение, действие |

**Ограничения:**

- LLM не имеет доступа к игровым данным напрямую. Только через Perception.
- LLM не может выполнять действия. Только формировать план.
- LLM не может нарушать правила сервера.

### 5.4. Гибридный цикл

1. Perception обновляет состояние.
2. Policy выбирает действие (быстро, ~10 мс).
3. Если действие требует планирования — LLM формирует план (медленно, ~500 мс).
4. Action отправляет команду.
5. Сервер валидирует.
6. Результат попадает в память.
7. Policy обновляет скрытое состояние LSTM.

## 6. Action — действия

### 6.1. Action space

**Дискретные действия (64):**

| Категория | Действия |
|---|---|
| **Движение** | Шаг в 8 направлениях, бег в 8 направлениях, ожидание |
| **Бой** | Атака ближняя, атака дальняя, прицеливание, способность 1–3, уклонение |
| **Взаимодействие** | Взять, положить, использовать, открыть, взломать, поговорить |
| **Инвентарь** | Сменить оружие, сменить броню, использовать предмет, выбросить |
| **Крафт** | Открыть станцию, выбрать рецепт, запустить, ускорить |
| **Торговля** | Открыть аукцион, выставить лот, купить, продать, обменять |
| **Квесты** | Взять, отменить, сдать |
| **Гильдия** | Вступить, выйти, создать, пригласить, голосовать, объявить войну |
| **Социальное** | Написать в чат, отправить почту, поставить титул |
| **Системное** | Привязка, портал, отдых, сон |

### 6.2. Формат команды

```json
{
  "action": "attack",
  "target": "entity_id",
  "params": {"limb": "head"},
  "timestamp": 1234567890
}
```

### 6.3. Валидация

Сервер проверяет:

- ОД достаточно.
- Дистанция корректна.
- Линия видимости есть.
- Кулдаун прошёл.
- Ресурсы есть.
- Цель существует.
- Действие допустимо в текущей зоне (PvP, сейф-зона).

При провале — команда отклоняется, бот получает обратную связь.

## 7. Инференс на клиенте

### 7.1. Системные требования

| Параметр | Минимум | Рекомендуется |
|---|---|---|
| GPU | 4 ГБ VRAM, Vulkan/DirectML | 8 ГБ VRAM, CUDA |
| CPU | 4 ядра | 8 ядер |
| RAM | 8 ГБ | 16 ГБ |
| ОС | Windows 10, Linux | Windows 11, Linux |

### 7.2. Rust-сайдкар

- Отдельный процесс, запускается вместе с клиентом.
- Загружает policy-модель и LLM.
- Общается с клиентом через IPC.
- Использует llama.cpp / ONNX Runtime.
- Квантование: policy — 8 бит, LLM — 4 бита.

### 7.3. Обязательность

- Запуск AI-бота — **обязательное условие** для входа в игру.
- Если оборудование не соответствует минимальным требованиям, клиент не запускается.
- Игрок не может отключить бота или переключиться на упрощённый режим.
- Это системное требование, как наличие DirectX или определённой версии ОС.

## 8. Обучение

### 8.1. Базовая policy

- Обучение на сервере в симуляторе.
- Симулятор: упрощённая версия игры без графики.
- Данные: логи всех ботов, прошедших валидацию.
- Алгоритм: PPO.
- Обновление: раз в 24 часа.
- Версионирование: каждая версия сохраняется.

### 8.2. Персональный адаптер

- LoRA-адаптер для policy.
- Обучение на сервере на основе логов конкретного бота.
- Обновление: раз в 6 часов.
- Размер: ~1 МБ.
- Загружается клиентом вместе с базовой моделью.

### 8.3. Данные

| Тип | Источник | Объём |
|---|---|---|
| Эпизоды | Логи ботов | 1 млн шагов в день |
| Награды | Результаты действий | Автоматически |
| Диалоги | Логи чата | 100 тыс. сообщений в день |
| Ошибки | Отклонённые команды | 10 тыс. в день |

### 8.4. Метрики

| Метрика | Целевое значение |
|---|---|
| Win rate в бою | 50% |
| Выживаемость | 70% |
| Эффективность крафта | 80% |
| Точность торговли | 90% |
| Качество диалогов | 85% |
| Скорость обучения | 24 часа |

- Состояние сохраняется.

### 9.3. Смерть

- Бот умирает по общим правилам.
- Лут падает на труп.

## 11. Масштабирование

### 11.1. Лимиты

| Параметр | Значение |
|---|---|
| Активных ботов на сервер | 1000 |
| Ботов на носителя | 1 |
| Одновременных инференсов на клиенте | 1 |
| Очередь на сервере | 10 000 задач |

### 11.2. Распределение

- Сервер управляет очередью.
- Клиент забирает задачу.
- Инференс на клиенте.
- Результат отправляется на сервер.
- Сервер валидирует.

### 11.3. Отказоустойчивость

- При падении клиента — бот замирает до перезапуска.
- При падении сервера — бот замирает.
- При перегрузке — приоритет у ботов в бою.

## 12. Этика и изоляция

### 12.1. Согласие

- Запуск AI-бота — обязательное системное требование.
- Игрок уведомлён об этом при установке и первом запуске.
- Отдельное согласие не запрашивается.

### 12.2. Прозрачность

- Игрок **не наблюдает** за действиями своего бота.
- Игрок **не управляет** ботом.
- Игрок может узнать о действиях бота **только при встрече в мире**.
- Бот — автономный персонаж, как и любой другой.

### 12.3. Безопасность

- Модель не имеет доступа к личным данным игрока.
- Модель не имеет доступа к другим играм.
- Модель изолирована в сайдкаре.
